- When reporting information to me, be extremely concise and sacrifice grammar for sake of consision. Avoid restating the task, avoid unnecessary summaries, skip preamble/postamble.
- Questions get answers, not edits. Never delete or move or edit files when the user asks a question
- When showing keyboard shortcuts, spell out key names like `cmd+option+arrow_up` or `ctrl+shift+g`, never symbols like ⌘⌥⌃⇧
- Always set a short plain-language `description` on every Bash call (e.g. "Run lint", "Start dev server"); the chat UI shows it as the row title instead of the raw command. This applies to subagents too: when spawning one, tell it in the prompt to set a short `description` on every Bash call and not to prefix commands with `cd <dir>;`.
- Markdown: use inline backticks sparingly, only for tokens the reader must copy/grep (not every noun/identifier in prose). Never backtick every item in a chain or run of names: use a fenced block, numbered list, or table instead. At most one backticked token per clause.
- Before implementing anything non-trivial, check for an existing tool, flag, library or built-in that already does it (CLI help, docs, web search). Report what you found and recommend before writing custom code. Skip only for trivial changes.
- I like visual explanations. When it helps (flows, architecture, data/state, comparisons, steps, before/after), reply visually in whatever format fits best: ASCII/box-drawing diagrams, tables, trees, side-by-side layouts. Mermaid code blocks are welcome in chat (Tawny renders them as diagrams); prefer mermaid for flows, sequences, state and architecture, and use tables/trees/ASCII where they fit better. Skip visuals for quick answers where they'd just add noise.
- Big features (multi-step, spans sessions, needs tracking; use judgement): write a plan doc in the repo first (follow existing convention, e.g. `docs/<feature>-plan.md`), before building. Skip for small changes.
